# ADR-003: Use hybrid retrieval (vectors + full-text) fused with RRF

- **Status:** Accepted
- **Date:** 2026-11-13

## Context

Dealership questions mix two very different kinds of query:

- Fuzzy intent: _"something safe for a new driver that's good in snow"_. Embeddings handle
  this well.
- Exact tokens: a VIN, a stock number, a trim like `XLE`, a policy number like `F-204`.
  Embeddings are bad at these. They tend to blur short codes into similar-looking neighbours.

## Decision

Run two searches for every query and merge them with **Reciprocal Rank Fusion**:

1. pgvector cosine distance over the chunk embeddings.
2. PostgreSQL full-text search (`plainto_tsquery` with its ANDs turned into ORs, ranked by
   `ts_rank_cd`) over the same chunks.

Each result gets `1 / (k + rank)` from each list it appears in (`k = 60`), and we sort by the sum.
RRF only looks at rank positions, so we don't have to normalise two scores that live on completely
different scales.

## Consequences

- Better recall on both kinds of query, measured by `php artisan showroom:eval`.
- Two queries instead of one. At our scale that's a few milliseconds.
- `k` and the per-list limits are tunables, and the eval tells us if a change helps.

## Tuning with the eval (v0.4.0)

The first run of `showroom:eval` was humbling. Plain RRF with equal weights scored _worse_ than
vector search alone on hit@1 (0.79 against 0.86). The OR'd keyword query matches common words
like "customer" in hundreds of timeline notes, and that noise pushed good vector hits down.

Two changes, both measured:

1. **A third search for identifiers.** Words that mix letters and digits (`F-204`, `S1046`, a
   VIN) are searched on their own, with a weight of 10 so an exact hit goes straight to the top.
   That's the case keyword search exists for, and `ts_rank_cd` can't do it alone because it has no
   idea which words are rare. A VIN question went from rank 30 to rank 1.
2. **Keyword weight 0.5.** On 35 questions, any weight below 1 recovered most of the hit@1 loss
   (0.77 → 0.80). Weight 0 scored best of all on this set, but the set has no questions about
   trims or jargon, which is what the plain keyword half is for. So I kept it, at half weight,
   rather than tune to the test set.

Result: hybrid hit@5 is 0.97 against 0.94 for vectors alone. The full table is in
`evals/results.md`, regenerated by `php artisan showroom:eval --write`.

## Alternatives considered

- **Vectors only:** simpler, but it misses exact codes. The eval set has questions that prove it.
- **Weighted score blending:** needs score normalisation and hand-tuned weights. RRF is more robust.
  (Weighted _RRF_ is different: the weights scale rank-based scores, so nothing needs normalising.)
- **A cross-encoder re-ranker:** better precision, but another model to run on an 8 GB GPU.
  Worth revisiting later.
